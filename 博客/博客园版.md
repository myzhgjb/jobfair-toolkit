# 招聘会岗位信息抓取与简历匹配的工程实践（附完整脚本）

> 本文记录一次真实场景的完整实现：从定位一场招聘会的数据源，到批量抓取 375 个岗位的 JD，再到按简历技术栈打分、生成可现场使用的清单页面。所有代码已开源。
>
> 仓库：https://github.com/myzhgjb/jobfair-toolkit


秋招跑招聘会最难受的不是人多，是**信息不对称**。

学校公众号推一篇《XX 招聘会即将举行，上百家企业等你来》，配图是几张模糊的展位照。你到场之后才发现：不知道有哪些企业、不知道每家招什么岗、不知道岗位要什么技术栈。只能一家一家走过去问，走到第三排就忘了第一排聊过什么。

我这次遇到的是一场区域性的青年人才对接会，官方口径"上百家企业"。我花了大概三个小时，把这场会的**89 家企业、375 个岗位、每一个岗位的完整 JD** 全部抓下来，按自己的简历打了对口分，做成一个手机上能勾选、能写备注的清单，然后发布成链接带去现场。

这篇文章把整个过程拆开讲，包括踩的坑。代码都是能直接跑的。

---

## 一、先搞清楚：这到底是一场什么会

这一步最容易翻车，而且翻车了后面全白干。

同一所学校、同一天，完全可能有两场不同的招聘会：

- **学院专场**（20–80 家）：只在学校的就业网（江苏是 91job）上挂，主办是某个学院，岗位高度集中在某个专业
- **市/区级综合场**（100–300 家）：走市人才办、区人才中心的公众号和独立平台，学校就业网**根本查不到**

判断方法就三条：

1. **看主办单位**。学院主办 = 专业限定；人才办/人社局主办 = 全行业综合。
2. **用企业数量级反推**。公众号说"300+"，但你在学校就业网上只数到 21 家 —— 那说明根本不是同一场。
3. **看场地**。体育馆是大型综合场，某栋楼的招聘大厅是小专场。

我这场是区级综合场，主办是园区人才办，承办方是当地的人力资源公司。这类活动通常有一个**独立的线上平台**，企业在那里报名、挂岗位。**这个平台就是数据源头**，比公众号推文靠谱一百倍。

> 一个反直觉的结论：**官方推文里的数字不要信**。推文写"上百家"，平台后台的报名数是 92 家，实际挂出岗位的是 89 家。另外 3 家报了名但没发岗位。你在页面上写 89，别写"上百家"。

## 二、找到数据入口：Vue SPA 的接口在哪

打开平台首页，按 F12 看 Network。这类政府/国企背景的平台，前端基本是 Vue + Element UI 的老架构，数据全走 XHR。

我的操作路径：

```
首页 → 找到这场活动的卡片 → 复制链接里的活动 ID
     ↓
活动详情页 → 点"学生进入" → 跳到"参会企业与岗位"页
     ↓
Network 里看到关键请求：GET /api/web/activity-stop/{stop_key}
```

这一下就拿到了全部数据 —— 89 家企业、375 个岗位，一个请求全在里面。

几个接口（以这个平台为例，其他平台思路相同）：

| 用途 | 接口 | 说明 |
|---|---|---|
| 活动详情 | `GET /api/web/activities/fair?key={fair_key}` | 返回活动名、日期、分会场列表、报名企业数 |
| **本场企业+岗位** | `GET /api/web/activity-stop/{stop_key}` | 一趟拿全，主力接口 |
| **岗位详情（JD）** | `GET /api/web/job/{url_key}` | 任职要求、职责、专业、HR 邮箱 |
| 平台全部岗位 | `GET /api/web/jobs?page=N` | 每页 15 条，不按招聘会过滤 |

**重点：列表接口没有 JD。**

这是第一个坑。`activity-stop` 返回的字段只有岗位名、薪资、学历、招聘人数、企业规模/行业/简介 —— **没有岗位职责，没有任职要求，没有专业要求**。

JD 在另一个接口里，必须拿每个岗位的 `url_key` 单独请求：

```python
def fetch_job_detail(url_key):
    url = f"https://campus.o-hr.com/api/web/job/{url_key}"
    req = urllib.request.Request(url, headers={"User-Agent": UA})
    with urllib.request.urlopen(req, timeout=25) as r:
        return json.loads(r.read().decode())["result"]
```

返回的字段里，这四个是关键：

- `description` → 任职要求（就是我们说的 JD 正文）
- `duty` → 岗位职责
- `new_majors` → 专业要求（**注意格式不统一**，有时是 `{"0":"计算机","1":"软件工程"}`，有时是 `["计算机"]`，两种都要兼容）
- `email` → HR 简历接收邮箱（这个平台居然没脱敏，直接是 `hr@公司域名`）

## 三、批量抓 375 个岗位的 JD：慢一点，但别被封

375 个请求，如果并发发出去，大概率被封 IP。

实际情况是我第一轮跑到 200 多条的时候开始返回 HTML 拦截页（不是 JSON），提示"您的 IP 最近有可疑的攻击行为"。这是典型的 WAF（创宇盾那一类），**封的是 IP，不是 UA**。换 User-Agent、改 GET/POST 都没用，只能等。

所以策略是：

```python
for i, key in enumerate(keys):
    if key in done:          # 断点续传：已抓过的跳过
        continue
    try:
        done[key] = fetch_job_detail(key)
    except Exception as e:
        fail.append((key, str(e)))
    time.sleep(0.45)         # 每次间隔 0.45 秒
    if (i + 1) % 20 == 0:    # 每 20 条额外歇 3 秒
        time.sleep(3)
    if (i + 1) % 10 == 0:    # 每 10 条落盘一次
        json.dump(done, open(OUT, "w"), ensure_ascii=False)
```

三个细节别省：

1. **每 10 条落盘**。不然跑到 300 条挂了，前面全白跑。
2. **中断后重跑能续**。判断依据是这条岗位有没有 `description` 字段，有就跳过。
3. **失败的单独重试**。我第一轮 374 条里挂了 2 条，单独重试两次都成功了。

375 条跑完大概 4 分钟。成功率 100%。

## 四、按简历打分：规则比模型靠谱

拿到 375 个岗位，直接看是看不完的。需要按"我这个背景，哪些岗值得投"排序。

我先试过用关键词直接匹配，结果很糟：

- 「数字后端工程师」被判成 Java 后端 —— 实际是 IC 物理设计（APR、floorplan、GDS）
- 「UI/UX 设计实习生」因为 JD 里提到"前端"被判成开发岗
- 「机械测试实习生」被判成软件测试

**纯关键词匹配一定会误伤，必须加否决词。**

最后用的规则是三层：

### 第一层：从简历判断主攻方向

把简历里的技术词按"簇"归类，统计每个簇的命中次数：

```python
CLUSTERS = {
    "backend":  [r"\bjava\b", r"spring", r"mybatis", r"redis", r"微服务", r"后端"],
    "frontend": [r"前端", r"\bvue\b", r"\breact\b", r"javascript"],
    "ai":       [r"\bagent\b", r"大模型", r"\bllm\b", r"\brag\b", r"pytorch", r"算法"],
    "embedded": [r"嵌入式", r"单片机", r"stm32", r"固件", r"驱动"],
    "hardware": [r"硬件", r"电路", r"\bpcb\b", r"射频", r"\bfpga\b"],
    # ...
}
```

命中次数 ≥3 的取前两个作为主攻方向。我的简历跑出来是 `ai: 11, backend: 9`，判定主攻 `[ai, backend]` —— 和我的求职意向（Java 后端 / AI Agent）一致。

### 第二层：岗位打分

```
5 分：岗位名直接命中主攻方向，或 JD 里明确要求该技术栈
4 分：JD 提到主攻方向，或命中次要方向
3 分：与主攻相邻（后端↔测试、嵌入式↔硬件）
2 分：技术岗但方向不同
0 分：非技术 / 明确不对口
```

### 第三层：否决词

这几条是血泪：

```python
VETO_BY_DIR = [
    # 主攻不是芯片时，"数字后端/版图/封装"一律排除
    (r"数字后端|版图|封装|晶圆|光刻|刻蚀|工艺整合|\bpie\b|\bdft\b", "chip"),
    (r"机械|结构设计|模具|流体|液冷|热设计", "mechanical"),
    (r"生物|细胞|分子|药理|制剂|发酵|纯化", "bio"),
    (r"\bbim\b|建筑|土建|平面设计|视觉设计|\bui/ux\b|品牌|文案|内容创作", "design"),
]
```

还有一个**学历降档**：要求硕士的岗位自动降 2 档。我是本科，不能让自己的清单里排一堆硕士岗。

跑完的结果：375 个岗位里 **49 个对口（≥3 分），涉及 28 家企业，其中 5 分只有 10 个**。

说实话这个数字比我预期的少。但这是真实的 —— 那场会是半导体和高端装备的主场，纯 Java 后端岗位本来就少。**诚实的匹配结果比好看的结果有用**，知道自己该在哪几家多待十分钟，比在 89 家里乱转强。

## 五、做成一个能打勾的清单

前四步产出的是数据，最后要变成现场能用的东西。

我的需求很具体：

- 企业名前面要有**空位**，投完打勾
- 每家旁边要有**空白**，写 HR 说了什么、什么时候笔试
- 关掉页面再打开，勾选还在

技术上就是 localStorage：

```javascript
const KEY_CK = 'jf-20261120.check.v1';
let ck = JSON.parse(localStorage.getItem(KEY_CK) || '{}');

document.addEventListener('change', e => {
  const cb = e.target.closest('[data-ck]');
  if (!cb) return;
  ck[cb.dataset.ck] = cb.checked;
  localStorage.setItem(KEY_CK, JSON.stringify(ck));
});
```

两个细节：

1. **key 必须按场次区分**。`jf-20261120` 和 `jf-20261206` 不能共用一个，不然上一场的勾选会串到这一场。
2. **要有导出功能**。纯静态页的数据在浏览器里，换个设备就没了。加一个「导出记录」按钮，生成 Markdown 方便复制到备忘录或者发给别人。

还有一个设计上的坑，我一开始犯错了：

> **默认必须显示全部企业，不能默认"只看对口"。**

我第一版默认筛选是"只看对口"，结果 89 家只显示了 26 家。用户打开第一反应是"你把不对口的企业删了？"。

正确的做法是：**全部都在，对口的排前面 + 标色条 + 打星**。想看纯对口的，下拉里自己选。

这个道理放到任何"筛选"功能上都成立：**默认视图要完整，筛选是可选动作，不是默认动作。**

## 六、发布到手机

生成的是单文件 HTML，不依赖任何 CDN，断网也能开。

发布用 WorkBuddy 的「发布为应用」，拿到 https 链接，手机浏览器打开 →「添加到主屏幕」，就是一个全屏的应用图标。

现场用起来是这样的：进馆前打开，按对口分排序，从 5 分的开始走，聊完一家打一个勾，备注写"HR 说下周笔试"。走到一半发现某家岗位不错，展开看 JD 和投递邮箱。

## 七、踩坑清单（可以拿去避雷）

| 坑 | 表现 | 解法 |
|---|---|---|
| 详情接口没有批量 | 列表里没有 JD | 逐岗请求 `job/{url_key}` |
| WAF 封 IP | 返回 HTML 不是 JSON | 间隔 0.45s，每 20 条歇 3s，别并发 |
| 专业字段两种格式 | dict / list 都有 | 都转 list 再 join |
| 平台把研发岗挂在"储备干部" | 分类全错 | **岗位名优先于平台类别** |
| 「数字后端」不是 Java 后端 | 匹配误伤 | 加否决词 |
| JS 变量名和元素 id 同名 | 下拉框点了没反应 | 用 `document.getElementById()`，别用同名全局变量 |
| Windows 上截图宽度≠视口宽度 | 以为页面溢出 | 用 iframe 固定宽度读 `scrollWidth` |

最后一条特别值得说：`let flt = 'all'` 同时又写了 `<select id="flt">`，然后 `flt.onchange = ...` —— 这个 `flt` 指的是字符串，事件根本绑不上去。页面看着正常，下拉框就是没反应。我排查了半天才发现是变量遮蔽。

## 八、换一场会怎么复用

这套流程不绑定具体哪场会。换一场，改三个参数：

```bash
# 1. 找活动
python fetch_campus.py discover

# 2. 抓企业 + 岗位
python fetch_campus.py fetch --fair-key <KEY> -o jobfair.json

# 3. 补 JD（必须做，不做少一半信息）
python fetch_campus.py detail --in jobfair.json

# 4. 按简历打分
python match_resume.py --jobs jobfair.json --resume resume.txt --report

# 5. 生成页面
python build_page.py --in jobfair.json -o 投递清单.html \
  --event-name "XX 双选会" --date "12月6日" --place "XX 体育馆" \
  --profile "Java 后端 / AI Agent"
```

**注意第 3 步不能省。** 我做过对比：不抓 JD 时对口岗位只有 33 个（5 分 4 个），抓完 JD 变成 49 个（5 分 10 个）。因为很多岗位名字就叫"软件工程师"，光看名字判不出方向，必须看 JD 里写没写 Java。

## 最后说两句

这套东西的价值不在于"抓了多少数据"，而在于**把时间从"找信息"挪到了"判断哪家值得聊"**。

89 家企业你不可能都聊，一天能认真聊 15 家就算多了。真正要做的是：提前知道哪 15 家值得排队，现场按顺序走，聊完记下来。

至于"对口岗位只有 49 个"这件事 —— 信息透明之后你会更焦虑，因为你发现选择没想象中多。但这总比在现场被人流推着走、回家才后悔"那家好像挺合适"要好。

**数据不会让机会变多，但会让你不浪费机会。**
